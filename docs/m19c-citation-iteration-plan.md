# M19C 引用范围失败：迭代优化计划

日期：2026-10-13；实施更新：2026-10-18 至 2026-10-19。状态：主要工程改动和完整评测已落地；最终自动检查通过 66/100，80% 验收目标未完成，人工标注审计与正式成功率仍待复核。新答案协议保留为显式实验开关。实施记录见 [引用优化交付记录](m19c-citation-iteration-delivery.md)。

目标：让当前问题的每项必需事实对应实际可见、直接支持它的原文，并在证据不足时进行有界补检或明确拒答。引用来源真实性、知识库权限、事实支撑和任务完成状态分别验证。

## 当前证据与问题定义

基线为 runId `32f8bad1-980c-4849-a0ea-000134d6558f`，固定 100 题、249 个 READY chunks，自动约束通过 56 题，39 题触发 `CITATION_OUTSIDE_ACCEPTABLE_RANGE`。正式 TaskSuccessRate 仍待独立人工复核。

现有运行时 `CitationValidator` 验证 C# 格式和是否来自已注册证据；评测侧 `RagAccuracyEvaluator` 还要求使用的每个 chunkId 属于任务的 `acceptableChunkIds`，人工事实覆盖也绑定 `supportingChunkIds`。因此，真实且格式合法的引用仍可能不支持当前事实，或被不完整的来源标注排除。

按末轮登记证据做原文字符串诊断：

| 诊断分组 | 任务数 | 下一步判断 |
|---|---:|---|
| 标注片段及全部标注原文已在登记证据中，仍引用到范围外 | 9 | 核查引用选择、额外背景陈述、重叠来源与实际生成输入 |
| 全部标注原文可见，但部分标注 chunk ID 未出现 | 2 | 核查同文档等价来源与标注完整性 |
| 未见全部标注原文 | 28 | 区分候选未召回、排序/预算丢失、场景歧义及其他合法表达 |

20/39 题同时引用了允许和范围外片段，此统计与上表重叠。三模式失败分布为 Retrieval-First 8、ReAct 18、Plan-Execute-Reflect 13。所有可回答任务中，当前标注原文完整可见为 53/89；这只是字符串诊断，不能代替事实正确性或引用语义复核。登记证据也不等同于每次模型调用的最终实际输入，需补充阶段观测。

例子：

- `AGENT-053`：末轮登记 273、288，目标 274 未出现；答案仍给出“六点”并引用 273。需要缺口补检和事实支撑检查。
- `AGENT-074`：67、256 的目标证据已经可见，答案同时引用 257 并扩展背景。需要逐项绑定与精简无关陈述。
- `AGENT-001`：书名/作者问题没有取得 250 的来源头部，引用了两本书的叙事片段。需要元数据意图和文档定位。
- `AGENT-078`：离线分析发现 263 对 264 的原文锚点等价候选。尚未确认其完整答案与所有引用正确，需独立复核。

## 迭代 0：逐题定位与标注审计

交付一份 39 题的问题台账，每题指定一个主要根因、允许附加次要原因：候选漏召回、错误文档/场景、上下文丢失、事实引用错配、额外引用、重叠来源或题意/标注歧义。

补充 benchmark 阶段观测：实际检索查询与各子问题候选、文档/排名、过滤及截断原因、每次模型调用的输入哈希与可见 citation IDs、最终事实与引用关系。生产使用脱敏摘要和哈希；详细查询只在已确认的公开 benchmark 中输出，不记录隐藏推理。

标注审计依据冻结源文独立开展。等价来源必须验证同文档、同事实及必要上下文；存在多次相似事件时明确题意。经人工确认的修订记录新的 dataset/policy 版本、来源证明和差异，并建立对应基线；原 v2 结果继续保留。线上检索与引用选择只读取用户请求和当前知识库证据。

验收：39/39 有可检查的根因证据；明确真实失败与待复核候选。仅有标注原文字符串命中不能自动认定任务成功。

涉及：`AgentBenchmarkTrace`、`AgentBenchmarkRunner`、`RagQueryRetrievalService`、`RagContextBuilder`、`ToolExecutionContext`。

## 迭代 1：建立三模式共享的事实—证据绑定

内部采用结构化答案草稿：子问题/事实、答案文本、支持的 evidence ID 和原文句段。服务端从实际可见原文定位支持片段，生成可信的 source span；模型不提供可信文档元数据或字符偏移。

新增共享绑定校验器，分两层：

1. 确定性验证来源、版本哈希、当前可见性、原文片段存在、稳定 citation ID 和知识库权限。
2. 检查该片段是否支持对应事实，尤其是人物、说话者、事件、数量、单位、时间和跨文档比较。模型检查只作为运行时反馈，独立人工复核仍决定 benchmark 最终正确性。

引用由服务端依据验证通过的绑定渲染。比较结论分别绑定其各项事实输入；删除未被用户要求且没有必要补充信息的背景陈述。必需事实缺失则补检或明确未完成，不能靠删掉所需事实获得通过。

证据已经充分但引用错误时，允许一次答案修复；没有支持证据时转入有界补检。所有校验和修复模型调用计入原预算。第一版先保持外部响应与现有原文前缀快照兼容，source span 作为内部校验数据。

验收：跨库、未知 ID、伪造原文片段、同人物不同事件、数量/单位矛盾等反例被阻止；合法引用与比较事实通过。9 题证据已可见组逐题复测，不预先承诺全部可恢复。

涉及：新增共享 `ClaimEvidenceBinding` / `ClaimEvidenceValidator`，接入 `CitationValidator`、`RetrievalFirstAgent`、`ReActAgent`、Plan `Executor` / `EvidenceCoverageVerifier`。

## 迭代 2：按事实目标取得正确文档与场景

将问题解析为子目标，保留实体、谓词、场景、时间和文档线索；多轮“他/她/继续同一场景”追溯用户原始主题。别名和跨语言扩展仅用于检索，最终事实仍需源文支持。

区分书名/作者等来源信息与正文情节。文档定位后，有界读取当前知识库 READY 文档的来源头部；作者由真实源文确认，不能用上传者等字段代替。

分离候选池与最终上下文数量，实验比较候选池大小以及重排开关。跨文档/多子目标保留各自证据名额。缺少某个事实时，用该缺口定向搜索；事件接近片段边界时读取已授权邻居，并验证其相关性。

先选择更合适的完整片段，保持现有前缀来源证明。若后续采用片段中部摘录，必须增加原文 offset/hash 证明和旧报告回放兼容，不能把未进入模型输入的全文当作引用依据。

验收：将“候选有支持来源却未进入上下文”与“候选本身缺失”分别统计。阶段目标是当前 53/89 的标注原文可见率提升到至少 80/89；这是诊断目标，仍须逐题语义验证。

涉及：`RagRetrievalQueryPlanner`、`RagQueryRetrievalService`、`SearchKnowledgeBaseTool`、`GetChunkContextTool`、`RagContextBuilder`。

## 迭代 3：重规划时调度证据窗口

将稳定来源登记表与当前生成证据窗口分离：来源 ID、版本、已展示快照保留审计；当前窗口按子目标选择证据并受 token 上限约束。

来源登记表也设置独立硬上限；当前窗口沿用现有片段数/token 配置。新配置、登记语义和实际输入预算均进入报告，工具、模型调用和重规划上限继续生效。

一次重规划时保留已经验证、仍与目标相关的证据，替换无关片段，为缺口留出空间。恢复已移出窗口的来源时复用稳定 ID，并重新展示真实正文及计入预算。

ReAct 同时压缩旧工具响应正文，保留工具请求/响应配对；Plan 从当前选定窗口构建综合输入。预算校验覆盖模型实际收到的证据正文，避免登记表看似达标而历史工具正文不断累积。

验收：预算已满时，新检索取得的关键片段能够进入生成窗口；原已覆盖子目标不会无故丢失。引用 ID 不重分配，单次输入符合原预算，Plan 仍最多一次重规划。

涉及：`ToolExecutionContext`、`ReActAgent` 消息组装、Plan `Executor.RunState` 与综合输入。

## 迭代 4：验证修复与完整验收

覆盖检查输出不符合 JSON/schema 时，记录安全的验证错误枚举，允许一次带明确格式反馈的修复，计入模型调用预算。数量、原文存在和来源绑定尽量用确定性规则检查；语义检查明确区分支持、矛盾、未知。

分别表达执行结束、事实完成、资料不足拒答和部分回答；必需事实未解决时，附加免责声明不能使任务被认定为成功。保持现有 API 与历史报告兼容，并由独立复核确认拒答是否正确。

先复测 39 题并检查原先通过任务的回归，再完整跑固定 100 题。每轮只改变一个主要机制，冻结配置、语料、数据、代码及观察；记录新增通过和新增失败，避免仅展示被修好的题。完成独立 Audit 与全部所需人工复核。

验收目标：

- 引用范围失败从 39 降到不超过 10，作为工程目标，不替代真实任务成功率。
- 当前 56 条自动约束通过至少净增 24 条；运行错误、工具约束、拒答与受限重规划继续完整报告。
- 正式总体 TaskSuccessRate ≥80%，三个模式分别报告成功率。
- 建议增加逐模式 ≥80% 的发布门槛：RF 24/30、ReAct 28/35、Plan 28/35，分别需要比当前净增 3、11、10。该门槛是建议，原需求只强制总体 ≥80% 并单独报告各模式。
- 人工复核未完成时，正式成功率保持 N/A；自动通过不能冒充正式任务成功。

## 推荐推进顺序

先完成迭代 0，再做共享事实绑定；随后改善检索和证据窗口，最后修复验证协议并完整验收。ReAct 的 18 个、Plan 的 13 个引用范围失败是主要优化对象。模型与重排对照目前没有足够收益证据，下一轮优先投入证据链改进。

每个迭代交付独立代码变更、针对性回归、完整评测对照和失败台账；任务与事实不写入生产逻辑。
